### 1:00–4:15 · Part 1: What it is, and where it lives
**Marker:** [VOICEOVER + SLIDE] / [VOICEOVER + SCREEN]

*Cue: divider "01 · What is CLAUDE.md"*
> Part one. What is CLAUDE dot M D?

*Cue: slide "Persistent instructions"*
> Every Claude Code session starts with a fresh context window. Nothing from yesterday's conversation comes along.
> CLAUDE dot M D is how you carry knowledge across sessions. It's a plain markdown file you write, and Claude reads it at the start of every session. Build commands, conventions, the gotchas of your project: written once, loaded every time.
> One thing to understand early: Claude treats it as context, not as enforced configuration. It reads the file and tries to follow it, but it's not a guarantee. If something must happen every single time, like a check before every commit, the docs point you to a hook instead. Hooks get their own episode later in the playlist.

*Cue: slide "CLAUDE.md vs auto memory"*
> There's a second memory system, and it helps to tell them apart. CLAUDE dot M D is written by you: instructions and rules. Auto memory is written by Claude: notes it takes from your corrections and preferences.
> Both load at the start of every conversation. You can browse both with slash memory, which lists your memory files and lets you open them in your editor.
> If you ask Claude to remember something, it saves it to auto memory. If you want it in CLAUDE dot M D instead, say so directly: add this to CLAUDE dot M D. Or open the file through slash memory and edit it yourself.
> And the docs make one point that runs through this whole episode: the more specific and concise your instructions, the more consistently Claude follows them.

*Cue: drawn file locations*
> So where do these files live? There are several places, from broad to specific.
> Your user file lives in your home folder, at dot claude slash CLAUDE dot M D. It applies to all your projects, and only you see it. Good for personal preferences.
> The project file lives in the project root, as CLAUDE dot M D, or inside the dot claude folder. This is the one your team shares through git.
> CLAUDE dot local dot M D, also in the project root, is for your personal notes on this one project, like your sandbox URL. Add it to dot gitignore so it isn't committed.
> Organizations can also set a managed policy file that applies to everyone, and you can put a CLAUDE dot M D inside a subfolder for instructions about that part of the code.

*Cue: slide "How they load"*
> They load from broad to specific: managed policy, then user, then project. Within a folder, the local file is read after the main one, so your personal notes come last.
> Files in the folders above where you launch Claude load at launch. Files in subfolders load on demand, when Claude reads or edits a file in that subfolder.
> To check what actually loaded, run slash context and look under Memory files.

### 4:15–7:30 · Part 2: What goes in it
**Marker:** [VOICEOVER + SLIDE] / [VOICEOVER + SCREEN]

*Cue: divider "02 · What goes in it"*
> Part two. What goes in it.

*Cue: slide "What belongs"*
> The docs put it well: treat CLAUDE dot M D as the place you write down what you'd otherwise re-explain. Add to it when Claude makes the same mistake twice, or when you type the same correction you typed last session.
> Four kinds of lines earn their place. Commands Claude can't guess: how to build, test, and lint. Code style rules that differ from the defaults. Architecture decisions specific to your project. And gotchas: behaviour that isn't obvious from reading the code. Workflow rules belong too, like "plan multi-file changes in PLAN dot M D first".
> On the cart project, that's lines like: run N P M test before committing. Prices are integer cents. Discount dates compare in the store's timezone. Each one is short, specific, and something Claude couldn't safely guess.

*Cue: slide "What stays out"*
> And what stays out. Long docs and tutorials: link to them instead. Anything Claude can figure out by reading the code, like a file-by-file tour of the project or standard language conventions. Information that changes often. Self-evident advice like "write clean code".
> And secrets. The project file is shared through git, so an API key in CLAUDE dot M D is an API key in your repository. Keep keys, tokens, and passwords out of it.

*Cue: slide "Keep it concise"*
> Why does length matter so much? Because CLAUDE dot M D loads every session, so every line costs context, every time.
> The docs give a target: under two hundred lines per file. Longer files consume more context and reduce adherence. Anthropic's guide goes further: bloated CLAUDE dot M D files cause Claude to ignore your actual instructions.
> The test for each line is one question. Would removing this cause Claude to make mistakes? If not, cut it.
> And if one rule keeps getting skipped, you can add emphasis, like the word IMPORTANT, to that one line. Emphasize everything, and nothing stands out.

*Cue: slide "Imports with @"*
> Last piece of part two: imports. A CLAUDE dot M D can pull in other files with the at sign followed by a path. For example: see at README for the overview, and at package dot json for the scripts.
> Relative paths resolve from the file that does the importing, and imported files can import others, up to four hops deep. If you want to mention a path without importing it, wrap it in backticks.
> One catch the docs are clear about: imports help you organize, but they don't save context. Imported files load at launch too. So a short file with imports still costs the same as one long file.

### 7:30–10:45 · Part 3: Review an existing CLAUDE.md
**Marker:** [VOICEOVER + SCREEN] / [VOICEOVER + SLIDE]

*Cue: divider "03 · Review a CLAUDE.md"*
> Part three. Reviewing an existing CLAUDE dot M D.

*Cue: drawn sample CLAUDE.md (before)*
> Here's a CLAUDE dot M D for our cart project. To be clear, I wrote this example for the course, and I put some problems in on purpose. It's the kind of file that grows when nobody prunes it.
> It opens with a paragraph of project history. Then: write clean, readable code. Use Node sixteen. A tour of every file in source. Run tests with N P M test. Prices are integers in cents, never floats. Be careful with the checkout code. Discount dates compare in the store's timezone. And, near the bottom, a payment API key.
> Let's go through it the way I'd review a pull request.

*Cue: slide "Spot the problems"*
> Start with the good lines, because there are some. "Run tests with N P M test" is a command Claude needs. "Prices are integers in cents" is a real gotcha that the code alone might not make obvious. "Discount dates compare in the store's timezone" is the decision we made in episode nine. Those stay.
> Now the problems. "Write clean, readable code" is vague and self-evident. It costs context and changes nothing. Cut it.
> "Use Node sixteen" is stale: in this example the project moved on, and a wrong instruction is worse than none. Fix it or cut it.
> The project history and the file tour are bloat. Claude can see where files live by reading the code. Cut them.
> "Be careful with the checkout code" is vague. Careful how? Either turn it into a rule you can check, or cut it.
> And if that checkout rule only matters when Claude works inside one folder, it doesn't need to load in every session at all. A CLAUDE dot M D in that subfolder loads on demand, only when Claude works there.
> And the API key is the worst line in the file. It's in git, so it's shared with everyone who has the repo. Remove it, and treat that key as exposed.

*Cue: slide "Tighten it"*
> Here's the tightened version. Under a commands heading: run N P M test before every commit, and N P M run lint. Under gotchas: prices are integer cents, never floats, and discount dates compare in the store's timezone. Under workflow: plan multi-file changes in PLAN dot M D first.
> It's a fraction of the length, every line passes the "would removing this cause mistakes" test, and the headings make it easy to scan, which the docs recommend: group related instructions under headers and bullets.
> Then check it. Run slash context and confirm the file shows up under Memory files. And over the next few sessions, watch whether Claude's behaviour actually changes. The guide says to treat CLAUDE dot M D like code: review it when things go wrong, and prune it regularly.
